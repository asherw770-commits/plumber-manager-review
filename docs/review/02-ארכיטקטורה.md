# ארכיטקטורה

## 1. תמונה כללית
```
 דפדפן / PWA (index.html + ui2.css + sw.js)                    לקוחות (order.html, ציבורי)
   │  Firebase Auth (אימייל+סיסמה)                                  │ POST /api/order
   │  Firestore SDK ישיר (קריאה/כתיבה לפי firestore.rules)          ▼
   ▼                                                        ┌──────────────────────┐
 Cloud Firestore  ◄──────── Admin SDK (עוקף כללים) ────────  │ Vercel Functions api/ │
   state/current, state/inbox, state/config, …               └─────────┬────────────┘
                                                                       │ Google Sheets API / Apps Script (גיבוי Drive) / Web Push
 Vercel Hosting: קבצים סטטיים, deploy אוטומטי בכל push ל-main
```
- **Frontend:** JavaScript רגיל (vanilla), קובץ אחד, בלי build ובלי תלויות npm. Firebase נטען כמודול מ-gstatic. העיצוב ב-`ui2.css` (נטען עם `?v=<hash>`; `tests/ui2-version-check.js` מאמת שה-hash עדכני).
- **Backend:** אין שרת מסורתי. הלקוח כותב ל-Firestore ישירות; **כללי האבטחה (`firestore.rules`) הם גבול ההרשאות**. פונקציות Vercel (`api/`) משמשות רק למה שאי אפשר מהלקוח: קבלת הזמנות מציבור, התראות Push, סנכרון גיליון, גיבוי, וקישור הסיווג.
- **פריסה:** `git push` ל-`main` → Vercel. לפני push רץ hook מקומי (`pre-push`) עם כל הבדיקות (`npm test` מריץ את אותה רשימה). **שים לב:** ה-hook אינו חלק מהריפו.

## 2. מבנה הנתונים (Firestore)
| נתיב | תוכן | קריאה | כתיבה |
|---|---|---|---|
| `users/{uid}` | פרופיל: `role`, `name`, `disabled`, `needsApproval`, `access` | המשתמש עצמו / admin | admin בלבד |
| `state/current` | **המסמך הראשי**: `tx[]`, `tasks[]`, `customerMeta{}`, `products[]`, `priceList[]`, `settlements[]`, `dailyNotes{}`, `_deletedIds[]` (מצבות), `_deletedAt{}`, `_dictUpdatedAt{}`, `clientVersion`, … | כל בעל תפקיד | admin (+owner במצב ישיר, מוגבל) |
| `state/inbox` | הודעות וואטסאפ (פוצל מ-current ב-1.10 בגלל מגבלת 1MB) | כמו current | כמו current |
| `state/config` | הגדרות: פרטי תשלום, `yehudaDirect`, `minClientVersion`, `workTypeMap`, `workCats` … | כל בעל תפקיד | admin; וגם השרת (Admin SDK) עבור קישור הסיווג |
| `state/owner_actions` | תור הפעולות של יהודה לאישור אשר (append-only מצד יהודה) | admin/owner | owner: הוספה בלבד; admin: ניקוי |
| `state/manager_notes`, `state/wa_archive` | הערות יחיאל; ארכיון וואטסאפ | admin (+manager להערות: הוספה בלבד) | |
| `auditLog/{id}` | יומן שינויי כסף — append-only | admin | admin/owner: יצירה בלבד |
| `orders`, `orderPhotos` | הזמנות מהטופס הציבורי | staff + owner | **רק השרת** יוצר; admin/owner מסמנים טופלה |
| `pushSubs` | מנויי Push | — | כל משתמש רק למכשיר שלו |
| `backups/{day}` | עותקים יומיים (14 אחרונים) | admin | admin |
| `serverSecrets/*`, `serverState/*`, `orderQuota/*` | סודות שרת / מצב שרת / מכסות | **אף לקוח** (ברירת מחדל: חסום) | רק Admin SDK |

אין מסד נתונים יחסי: כל שורה (עסקה, משימה) היא אובייקט בתוך מערך במסמך אחד. מזהים אקראיים (`uid()`); **סדר הכנסה נגזר ממיקום במערך ו-`createdAt`**, לא מה-id.

## 3. סנכרון ומיזוג — החלק הכי עדין בקוד
המסמך הראשי נכתב **כולו** בכל שמירה (אין עדכוני שורות בודדים). כדי שמכשירים שונים לא ידרסו זה את זה:
- לכל שורה `_updatedAt` ולכל קבוצת שדות `_fieldAt` (חותמות זמן מתוקנות בהפרש שעון מהשרת: `_clockOffset`).
- `mergeRowsById` / `mergeRowFields` / `mergeCloudDoc` ממזגים את הגרסה המקומית והענן **לפי שדה/קבוצת שדות**, עם **מצבות מחיקה** (`_deletedIds`, מוגבל ל-`TOMBSTONE_CAP=1500`) ושומר "שורה ישנה" (`STALE_ROW_GRACE_MS`) כדי לא להחזיר שורות שנמחקו ממכשיר ישן.
- `saveState` — כתיבה עם בדיקת התנגשות והגנות (`save-wedge`); `freshenState` — רענון לפני העתקת הודעה/יציאה, כדי שהודעה לא תכלול נתון ישן.
- **תור יהודה:** כשיהודה לא כותב ישירות, כל פעולה נוספת כרשומה ל-`state/owner_actions` (עם `arrayUnion`); אצל אשר היא ממוזגת לפי "הגרסה האחרונה של כל שורה" ו"לפי קבוצת שדות" (`_mergeOwnerActions`, `compactOwnerQueue`). הכללים מגבילים כל רשימה ל-500 פריטים.
- **גרסת לקוח:** `CLIENT_VERSION` נכתב לכל מסמך; `state/config.minClientVersion` גורם לכללים לדחות כתיבה ממכשיר ישן (מונע הזרקה מחדש של שורות שנמחקו).
- בדיקות: `merge-check`, `sync-check`, `sync-sim 300`, `sync-adversarial-check` (תרחישים עוינים + מטריצה אקראית), `integrity-check`, `owner-queue-check`, `fresh-check`, `save-wedge-check`.

## 5. פונקציות השרת (`api/`)
| קובץ | שיטה / אימות | תפקיד |
|---|---|---|
| `order.js` | POST ציבורי; מכסות (טלפון/IP/יום), honeypot | הזמנת לקוח → `orders` + Push ליהודה |
| `address.js` | GET ציבורי | ערים/רחובות מהמאגר הממשלתי (data.gov.il), עם מטמון |
| `push-key.js` | GET ציבורי | המפתח הציבורי ל-Push |
| `classify.js` | POST: גוף עם קוד סודי **או** `Authorization: Bearer <ID token>` של admin | סימון סוגי עבודה ע"י הבעלים; ניהול הקישור ע"י אשר |
| `sync-sheet.js` | GET + `CRON_SECRET` (cron יומי 06:00 UTC) | דחיפת הנתונים לגיליון Google |
| `sync-sheet-run.js` | POST + ID token של admin/owner | רענון הגיליון אחרי שינוי (לפחות דקה בין הרצות) |
| `backup-drive.js` | GET + `CRON_SECRET` (cron 20:50 UTC) | גיבוי לילי ל-Drive (דרך Apps Script) + בדיקת שלמות |
| `backup-drive-run.js` | POST + ID token של admin | בדיקת גיבוי ידנית |
| `_lib.js` `_syncCore.js` `_sheets.js` `_backup.js` `_integrity.js` | פנימי | |
| `_loadApp.js` | **כלי בדיקות בלבד** | טוען את הפונקציות האמיתיות מתוך `index.html` ל-Node (חילוץ פונקציות top-level) כדי שהבדיקות יריצו את הקוד האמיתי ולא עותק. כך גם סנכרון הגיליון בשרת משתמש באותו קוד חישוב. |

**משתני סביבה (Vercel; לא בריפו):** `FIREBASE_SERVICE_ACCOUNT` (JSON של חשבון שירות), `CRON_SECRET`, `BACKUP_WEBAPP_URL`.

## 6. תהליך הפריסה והסביבות
- סביבה אחת בלבד: ייצור. אין staging. כל push ל-`main` מתפרסם תוך ~דקה.
- `firestore.rules` **לא** מתפרסם אוטומטית; הבעלים מפרסם ידנית (`firebase deploy --only firestore:rules`). לכן יכולה להיות סטייה בין הקובץ בריפו לכללים החיים (נבדק ידנית באחרונה ב-16.10).
- הריפו מחובר ל-Vercel — **מי שיש לו הרשאת כתיבה ל-`main` יכול לפרוס לייצור**. לכן הבודק מקבל גישת קריאה בלבד / העתק.

## 7. ויתורים ארכיטקטוניים מודעים
- קובץ יחיד של 20K שורות ובלי build: פשוט לפריסה ולתחזוקה על ידי אדם אחד, אבל קשה לניווט/בדיקה ביחידות (לכן `_loadApp.js`).
- `unsafe-inline` ב-CSP (כל ה-JS inline).
- כתיבת מסמך שלם בכל שמירה (במקום שורות בנפרד) — מקור לרוב המורכבות במיזוג.
